# Pre-registration — one served-model contract, and R12 to detect its re-implementation

Written **before** any code in this branch was executed. Nothing below is a
measurement; every number this round produces lands in
`reports/R12_CONTROLS.md` and `reports/R12_FLEET.md`, generated by running the
code.

- branch: `feat/r10-served-contract`
- base: `main` @ `0ca5cae`
- authorization: A-1 (local CPU, no cloud, no GPU, no spend)
- compute: **no fits, no sweeps, no fine-tunes.** This round is pure
  architecture. The only executions are (a) the focused pytest files added
  here, and (b) `mlkit` running the new check against repos already on disk,
  which is an `ast` walk that imports nothing from those repos.

## What is being built

1. `src/resilient_mlkit/core/served.py` — the served-model contract as code:
   a `ServedModel` record with a self-hash, `verify_at_load`, a challenger
   decision whose `NA` is structurally distinct from `FAIL`, and a serve-arm
   guard where a closed arm refuses by construction.
2. `src/resilient_mlkit/core/served_reimplementation.py` — the `ast` scanner.
3. `R12` in `checks/readiness.py` — the portfolio check, phase `readiness`,
   placed in `PHASE_ORDER["readiness"]` immediately before `R8` (which reports
   and therefore stays last).

## The hypotheses, stated before measuring

**H1 (contract fires).** Each of the four contract clauses refuses on its
negative case: a tampered payload fails the self-hash; a data file whose
sha256 differs from the record fails provenance; a comparison with no measured
skill returns `NA`; a request for a closed arm raises.

**H2 (contract stays silent).** The same four clauses accept the legitimate
case: an untampered payload loads; a matching sha256 verifies; a measured
positive skill returns `PASS` and a measured non-positive skill returns
`FAIL`; a request for an open arm returns the arm.

**H3 (R12 fires).** The scanner reports a file that carries champion/
challenger/serve logic — an artifact self-hash, a promotion verdict, a
serve-arm decision, or a shadow router — without importing
`resilient_mlkit.core.served`.

**H4 (R12 stays silent).** The same file, changed in exactly one way — it
imports the contract and calls it — produces no finding.

**H5 (predicted fleet result, recorded before running).** R12 is expected to
FAIL on `resilient-chokepoint`, `resilient-torrent` and `resilient-fray`,
because those repos are the ones the motivating finding names as carrying
local serving definitions. `resilient-triage` is expected to FAIL as well:
it is the reference implementation, and being the best local copy is still a
local copy. No repo is expected to PASS, because nothing has adopted the
contract yet — this branch only defines it. **A PASS anywhere in this run
would be evidence the scanner is blind, not evidence a repo is clean**, and
would be reported as such.

## What would falsify this work

- R12 firing on a file that imports and calls the contract (H4 fails) — the
  check would be unadoptable, since adopting it would not clear it.
- R12 staying silent on `resilient-torrent/src/torrent/mlops/
  champion_challenger.py`, which is a re-implementation by inspection.
- Any of the four contract clauses passing its negative control.

## Explicitly out of scope

- **No existing check changes behaviour.** R1–R11 are untouched. The only edit
  to a shared file is one entry appended to `PHASE_ORDER["readiness"]`.
- **No adopter repo is edited.** `resilient-triage` is a colleague repo and is
  read-only here; `chokepoint`, `torrent` and `fray` adopt the contract on
  their own branches, after their own verifiers pass.
- **No tag.** The session lead cuts it.
